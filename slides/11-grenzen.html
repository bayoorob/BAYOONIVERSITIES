Grenzen / Was grün nicht bedeutet

Auch schlechte Architektur kann grün sein.

Der Test sieht

  • Die ausgewählten Typen
  • Die formulierten Beziehungen
  • Den konfigurierten Prüfumfang

Der Test beurteilt nicht

  • Ob die Architektur sinnvoll ist
  • Jede dynamische Laufzeitkopplung
  • Ob eine Ausnahme fachlich nötig ist

Reflection über Strings, DI-Verdrahtung und HTTP-Verträge brauchen gegebenenfalls andere Prüfungen.

Der Test kann eine Entscheidung zuverlässig bewahren und trotzdem die falsche Entscheidung bewahren. Grün heißt nur, dass die formulierte Regel für die ausgewählten Typen erfüllt ist. Es heißt nicht, dass die Architektur gut ist. Auch der Umfang zählt: Eine leere Auswahl, eine vergessene Assembly oder ein großzügiger Ausnahmepfad kann sehr überzeugend grün aussehen. Statische Typregeln sehen außerdem nicht jede dynamische Kopplung. Eine Klasse, die über einen String geladen wird, eine kaputte DI-Registrierung oder ein inkompatibler HTTP-Vertrag benötigt gegebenenfalls andere Tests. Zu restriktive Regeln können legitime Änderungen blockieren. Wenn das ständig passiert, sollte das Team die Regel oder die zugrunde liegende Entscheidung überprüfen, statt immer neue Ausnahmen anzuhängen. Insbesondere der Composition Root muss Implementierungen verdrahten dürfen. Ein pauschales API-darf-Infrastructure-nie-kennen wäre dafür oft zu grob. Architekturtests ergänzen also Code Reviews und Verhaltenstests. Sie ersetzen weder den Entwurf noch die Verantwortung dafür.
