„Das merkt doch keiner.“ Doch. 


namespace Shop.BusinessLogic;

public sealed class OrderService
{
    public Shop.Api.ApiDiagnostics? Diagnostics { get; set; }
}
FAIL BusinessLogic_Should_Not_Depend_On_Api
BusinessLogic must not depend on Api.

Grün prüfen. Typreferenz ergänzen. Rot sehen. Referenz entfernen. Wieder grün.

Ein unbenutztes using ist kein Gegenbeweis. Die Eigenschaft erzeugt eine echte Typabhängigkeit.

Die Demo startet mit dem normalen Testlauf. Die Regel ist grün. Anschließend aktivieren wir eine zusätzliche Eigenschaft im OrderService: Ihr Typ kommt aus Shop.Api. Das ist bewusst eine echte Typverwendung und kein unbenutztes using, das der Compiler möglicherweise gar nicht in die Assembly übernimmt. Der Anwendungscode kann weiterhin kompilieren, aber der Architekturtest wird rot. Danach deaktivieren wir die Verletzung und führen denselben Test erneut aus. Er muss wieder grün sein. Im beiliegenden Projekt lässt sich die Eigenschaft über eine Build-Eigenschaft zuschalten. So funktioniert dieselbe Vorführung ohne hektisches Editieren auf dem Beamer. Der mittlere Lauf soll fehlschlagen; das ist der Nachweis, dass die Regel überhaupt anschlägt. Wenn wir die Eigenschaft entfernen, aber der Test rot bleibt, haben wir noch keine erfolgreiche Demo, sondern einen zusätzlichen Fehler. Im Alltag reicht diese Probe einmal beim Einführen einer Regel und nach wesentlichen Änderungen ihres Scopes. Sie beantwortet die entscheidende Frage: Findet der Test die Verletzung, wegen der wir ihn überhaupt geschrieben haben? Die rote Ausgabe auf der Folie ist schematisch und dient auch als Ersatz, falls die Live-Umgebung gerade beschlossen hat, selbst Vortrag zu halten.
