Vertiefung / Fachliche Modulgrenzen

Kundenpersistenz ist kein Bestell-API.


[Fact]
public void Orders_Should_Not_Depend_On_Customer_Infrastructure()
{
    var assembly = typeof(Shop.Orders.Application.OrderService).Assembly;
    Assert.NotEmpty(assembly.GetTypes());

    var result = Types.InAssembly(assembly)
        .ShouldNot()
        .HaveDependencyOn("Shop.Customers.Infrastructure")
        .GetResult();

    Assert.True(result.IsSuccessful,
        "Orders must not depend on customer persistence.");
}

xUnit + NetArchTest.Rules · separate Orders.Application-Assembly · nicht Teil der kleinen Live-Demo

Diese Regel schützt eine fachliche Grenze statt einer technischen Schicht. Orders darf Kundenverträge verwenden, aber keine Kundenpersistenz. Die Assembly-Auswahl umfasst hier das ganze Bestell-Anwendungsprojekt; im Gegensatz zur Demo teilen sich nicht mehrere Module diese Assembly. Eine solche negative Regel verbietet genau den genannten Ziel-Namespace. Sie ist keine vollständige Positivliste aller erlaubten Abhängigkeiten. Wenn sich zwei Module eine Assembly teilen, muss die Quelle enger gefiltert und die gefilterte Auswahl auf Nicht-Leere geprüft werden. Der Grund für die Regel ist die unabhängige Änderbarkeit der Speicherung des Kundenmoduls, nicht die Existenz eines besonders schönen Interfaces.
