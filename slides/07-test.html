Das Diagramm bekommt eine Assertion.


[Fact]
public void BusinessLogic_Should_Not_Depend_On_Api()
{
    var assembly = typeof(OrderService).Assembly;
    var rule = Types.InAssembly(assembly)
        .That().ResideInNamespace("Shop.BusinessLogic");
    Assert.NotEmpty(rule.GetTypes());

    var result = rule.ShouldNot()
        .HaveDependencyOn("Shop.Api").GetResult();
    Assert.True(result.IsSuccessful,
        "BusinessLogic must not depend on Api.");
}

Imports: Xunit, NetArchTest.Rules, Shop.BusinessLogic · vollständiges Beispiel im Demo-Testprojekt

Der Test wählt zuerst die Assembly eines realen Anwendungstyps aus. Danach begrenzen wir die Quelle auf Shop.BusinessLogic, weil sich in der Demo mehrere Schichten dieselbe Assembly teilen. Assert.NotEmpty ist keine Dekoration: Wenn wir den Namespace später umbenennen und den Test vergessen, darf eine leere Auswahl nicht einfach grün werden. Die eigentliche Regel verbietet Typabhängigkeiten zum Namespace Shop.Api. GetResult führt sie aus, xUnit wertet das Ergebnis aus. Der String bezeichnet den tatsächlichen Namespace, nicht eine Package-ID und nicht automatisch den Projektnamen. Auswahl und Ziel müssen zur realen Anwendung passen. Ein Service aus einer anderen Assembly wäre kein geeigneter Anker, nur weil sein Name vertraut klingt. Die Prüfung startet keinen Webserver und keine Datenbank. Das gilt für diese Typregel, nicht pauschal für alle Architekturtests. Ein EF-Modellcheck kann andere Voraussetzungen haben. Jetzt interessiert uns vor allem, ob der Test eine echte Verletzung findet. Ein grüner Test ohne passenden Gegenbeweis ist zunächst nur ein sehr zuversichtliches Stück Code.
