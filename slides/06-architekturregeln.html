Aus dem Abhängigkeitsdiagramm abgeleitet

5 Architekturregeln für unser Shop-Backend

Regel Warum?
  1. Controller dürfen nicht auf den DbContext zugreifen. Datenbankzugriffe gehören in die BusinessLogic. So umgehen Controller keine Geschäftslogik.
  2. Controller dürfen nicht auf Entities zugreifen. Die API soll nicht vom internen Datenmodell abhängen. Dafür verwenden wir DTOs aus ApiObjects.
  3. Services dürfen nicht von Controllern abhängen. Die BusinessLogic bleibt unabhängig von der API und wiederverwendbar.
  4. Services dürfen nicht direkt vom DbContext abhängen, wenn der Zugriff über einen anderen Service erfolgen soll. Fachliche Zuständigkeiten bleiben getrennt. Ein Service soll nicht die Datenzugriffe anderer Services übernehmen.
  5. Entities dürfen nicht von API oder BusinessLogic abhängen. Das Datenmodell bleibt unabhängig von höheren Schichten. API-Änderungen erzwingen so keine Änderungen an Entities.
Diese fünf Regeln übersetzen die erlaubten und verbotenen Abhängigkeiten aus dem Diagramm in überprüfbare Aussagen. Controller greifen weder direkt auf den DbContext noch auf Entities zu; die API verwendet dafür DTOs aus ApiObjects. Services hängen nicht von Controllern ab und bleiben dadurch unabhängig von der API. Wenn Datenzugriff zu einem anderen Service gehört, soll ein Service dessen Zuständigkeit nicht umgehen und direkt den DbContext verwenden. Entities bleiben unabhängig von API und BusinessLogic, damit Änderungen an höheren Schichten das Datenmodell nicht erzwingen. Die Regeln schützen getrennte Zuständigkeiten und unabhängige Änderungen, nicht bloß eine bestimmte Namenskonvention.
