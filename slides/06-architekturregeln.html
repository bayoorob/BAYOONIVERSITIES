4 Architekturregeln für unser Shop-Backend

Regel Warum?
  1. Controller dürfen nicht auf den DbContext zugreifen. Datenbankzugriffe gehören in die BusinessLogic. So umgehen Controller keine Geschäftslogik.
  2. Controller dürfen nicht auf Entities zugreifen. Die API soll nicht vom internen Datenmodell abhängen. Dafür verwenden wir DTOs aus ApiObjects.
  3. Services dürfen nicht von Controllern abhängen. Die BusinessLogic bleibt unabhängig von der API und wiederverwendbar.
  4. Entities dürfen nicht von API oder BusinessLogic abhängen. Das Datenmodell bleibt unabhängig von höheren Schichten. API-Änderungen erzwingen so keine Änderungen an Entities.
Aus unserem Abhängigkeitsdiagramm lassen sich fünf konkrete Architekturregeln ableiten. **Regel 1: Controller dürfen nicht auf den DbContext zugreifen.** Datenbankzugriffe gehören in die BusinessLogic, nicht in unsere Controller. **Regel 2: Controller dürfen nicht auf Entities zugreifen.** Wir verwenden stattdessen DTOs aus ApiObjects, damit API-Verträge und internes Datenmodell getrennt bleiben. **Regel 3: Services dürfen nicht von Controllern abhängen.** Unsere BusinessLogic soll unabhängig von der API funktionieren und wiederverwendbar bleiben. **Regel 4: Entities dürfen nicht von API oder BusinessLogic abhängen.** Unser Datenmodell soll unabhängig von den darüberliegenden Schichten bleiben. Diese Regeln sind bewusste Architekturentscheidungen, die wir anschließend automatisiert überprüfen können.
